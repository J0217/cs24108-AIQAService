# 演示模式说明（本地 / 微信开发者工具）

> 适用场景：课程实验演示、答辩录屏、组内联调。系统不面向真实客户，
> 因此演示阶段的首要目标不是"接最贵的模型"，而是"**任何一次点击都有确定的响应**"。

## 1. 要解决的问题

真实服务商（如 `agnes-ai.cn`）对免费/低价账号的并发与频率限制很严：实测连发两条消息，第二条即返回 `429 Too Many Requests`；
静默 45 秒后单发一问又正常（827ms）。表现为：**第二条提问突然变成"抱歉，我暂时无法回答"**，演示现场极易被误判为系统故障。

这既不是代码 bug，也不该靠"现场手速慢一点"来回避。工程上要做的，是让演示链路**不依赖那个不稳定的外部环节**。

## 2. 三种模式

| 模式 | 外部依赖 | 响应 | 适合 |
|---|---|---|---|
| 本地模拟模型（推荐默认） | 无（仅本机 5001 端口） | 350–900ms，稳定 | 演练、录屏、答辩主线 |
| 真实服务商 | 需外网 + 余额 | 秒级，可能 429 | 证明"真能调模型"的那 1–2 次 |
| 纯模板（无 Key） | 无 | 7ms 级 | 证明成本控制与降级策略 |

三者的代码路径**完全相同**：都是 `AIService._call_ai_api()` 发 HTTP → 解析 JSON → 估算置信度 → 落库。
差别只在 `AI_API_BASE_URL` 指向哪里。这也是软件工程里的标准做法——用 **桩服务（stub）** 替代不稳定的外部依赖，而不是把业务代码改烂。

## 3. 操作步骤

### 3.1 演示主线：本地模拟模型

```powershell
# 窗口 1：模拟模型服务（保持运行）
cd D:\cs24108-AIQAService
py -3.14 tools\mock_llm_server.py

# 窗口 2：切配置 + 启动后端
py -3.14 tools\use_ai_mode.py --mock
py -3.14 backend\app.py
```

`--mock` 只改 `.env` 里的 `AI_API_BASE_URL` 和 `AI_MODEL` 两行，**不动 AI_API_KEY**，并把原来的真实配置备份到 `instance/ai_mode_backup.json`。

自检：

```powershell
curl http://127.0.0.1:5001/health
py -3.14 tools\use_ai_mode.py --status
```

### 3.2 需要展示真实模型时

```powershell
py -3.14 tools\use_ai_mode.py --real      # 从备份恢复真实服务商
py -3.14 tools\prewarm_cache.py           # 先预热，把回答缓存下来
```

`prewarm_cache.py` 会按 `DEMO_QUESTIONS` 里的问题逐条提问（默认间隔 4 秒，避免触发限流），
把模型回答写入 `instance/ai_reply_cache.json`。之后现场再问同一批问题，**直接命中缓存**，
毫秒返回、不花钱、不受限流影响。

> 演示提示：真实模型环节只问 1–2 个问题，问完立刻切回模板类问题（订单查询、退换货政策），节奏最稳。

### 3.3 纯模板模式（对照组）

把 `.env` 中 `AI_API_KEY` 改成 `your-ai-api-key-here` 后重启，`_ai_configured()` 判定为占位值，
走本地模板 + 兜底话术。答辩时可现场演示"配了 Key / 没配 Key"的对比。

## 4. 兜底机制（就算是真实模型也不会翻车）

| 机制 | 位置 | 行为 |
|---|---|---|
| 429/5xx 退避重试 | `ai_service._call_ai_api` | 最多 3 次，优先采用响应头 `Retry-After`（上限 8s） |
| 回复缓存 | `ai_service._cache_get/_cache_set` | 同一问题 24h 内不再请求模型 |
| 模板兜底 | `generate_reply` 第 3 步 | 模型失败时返回最佳匹配模板（置信度 ≥0.6） |
| 场景兜底话术 | `_get_default_reply` | 完全没有匹配时返回场景化提示，引导补充信息 |

四级顺序：**高置信模板 → 回复缓存 → 大模型 → 模板/兜底**。成本与该顺序一致递减。

## 6. 答辩可能被追问

**"你这是不是假的大模型？"**
> 演示链路用的是本地桩服务（stub），接口协议与 OpenAI 完全一致，走的是同一套 HTTP 调用、解析、落库代码。
> 真实服务商我也跑通过，日志里有 `大模型回复成功，置信度=0.90，耗时=1102ms`，并且真实调用会受服务商限流，这正是我们加缓存和重试的原因。
> 用桩是为了让演示可控，属于测试替身（test double）的标准用法，不是绕过功能。

**"缓存会不会答错？"**
> 缓存键是「场景 + 归一化问题文本」，只缓存模型自己生成过的答案，不跨问题复用；默认 24 小时过期，模型换了配置自然失效。

**"为什么不干脆只留模板？"**
> 模板命中率有限，遇到没写过的问法就答不上；模型负责长尾。两者叠加才是成本与覆盖面的折中。

## 7. 边界（如实说明）

- 本地模拟服务**不是真模型**，不做语义推理，只保证协议与链路真实；
- 回复缓存是**进程外文件 + 进程内字典**，多实例部署时各自独立，生产环境应换 Redis；
- 缓存不区分会话，只区分场景与问题文本，因此不会带入上下文，长对话追问仍会走模型。
